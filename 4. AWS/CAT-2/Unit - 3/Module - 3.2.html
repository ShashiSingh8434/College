AWS Identity and Access Management (IAM)

Control who can do what on your AWS account — securely and granularly

1.1 Definition & Purpose

Definition
AWS IAM (Identity and Access Management) is a global AWS service that enables you to manage who (identity) can access AWS resources and what (access) they are allowed to do — without incurring additional cost.

Why IAM is Required

  • AWS accounts can host dozens of services (EC2, S3, RDS, Lambda…)
  • Multiple users (developers, admins, auditors) need different levels of access
  • Without IAM, every user would need the root account credentials — a catastrophic security risk
  • IAM provides granular control: each user/service gets only what it needs
  • Supports compliance requirements (least privilege, audit trails)

Key Concepts Before Components

🪪 Identity
Who you are — a user, group, role, or service. The subject requesting access.
🔑 Access
What you can do — read, write, delete, execute. The action permitted on a resource.
✅ Permission
A granted right to perform a specific action on a specific resource.
🔐 Authentication
Verifying who you are — "Prove your identity."
🛂 Authorization
Determining what you can do — "You are allowed to do X."
📄 Policy
A JSON document defining what is allowed or denied on which resources.

1.2 Authentication vs Authorization

🔑 Important DistinctionThese two concepts are often confused but are fundamentally different steps in the security flow.

🌍 Real-World Analogy
  • Authentication = Showing your ID card at the office building entrance — security confirms you work there
  • Authorization = Your ID card only lets you access floors 1–3, not the server room on floor 5

1.4 Root User

Definition
The root user is the initial account owner identity created when an AWS account is first set up. It uses the email address and password used to create the account and has unrestricted access to all AWS services and resources.
Why Root Has Extensive Privileges
  • It is the account's original owner identity
  • Can perform actions no other user can — e.g., close the account, change account settings
  • Can access all services with no permission restrictions
  • Acts as the "super administrator" of the AWS account
Security Best Practices
  • Never use root for day-to-day tasks
  • Enable MFA on root immediately after account creation
  • Create IAM admin users for routine administration
  • Lock away root credentials (store securely, rarely accessed)
  • Root has no IAM permissions restrictions — extremely dangerous if compromised
⚠️ Tasks ONLY Root Can Perform Close AWS account  |  Change account email / password  |  Enable MFA delete on S3  |  Restore IAM user permissions  |  Activate IAM access to billing

1.5 IAM Users

Definition
An IAM User is a persistent identity within an AWS account representing a specific person or application. It has long-term credentials (username/password or access keys) and is granted specific permissions.

What a User Represents

  • A specific human (e.g., Alice the developer, Bob the DBA)
  • An application or service running outside AWS needing programmatic access
  • A system account for automation scripts

User Credentials — Two Types

Credential TypeUsed ForComponents
Console PasswordAWS Management Console (web UI) loginUsername + Password (+MFA)
Access KeysProgrammatic access (CLI, SDK, API)Access Key ID + Secret Access Key

When IAM Users Are Appropriate

  • Human users who need to sign into AWS Console
  • Applications running outside AWS that need API access
  • Cross-account access when roles aren't feasible
  • NOT recommended for applications running on AWS services (use Roles instead)
📌 Key RelationshipAn IAM User by itself has NO permissions. Permissions must be explicitly granted via policies — either directly or through group membership.

1.6 IAM Groups

Definition
An IAM Group is a collection of IAM users. Policies attached to a group apply to all users in that group. Groups are used to manage permissions for multiple users efficiently.

Why Groups Simplify Administration

  • Assign one policy to the group → all members inherit it instantly
  • When a user's role changes, move them to a different group
  • No need to update permissions for individual users one by one
  • Easier to audit — look at one group to understand all its members' permissions
Groups Simplify Permission Management
Developers Group
S3 Read+Write, EC2 Full		 Auditors Group
Read-Only All Services		 Admins Group
Full Access All
Alice, Bob, Charlie Dave, Eve Frank

Important Rules About Groups

  • A user can belong to multiple groups
  • Groups cannot contain other groups (no nested groups)
  • Groups have no credentials — they are purely a permission management mechanism
  • Policies are attached to the group, not the individual user

1.7 IAM Roles

Definition
An IAM Role is an identity with specific permissions that can be assumed by trusted entities (AWS services, users, or external identities). Unlike users, roles have no long-term credentials — they provide temporary security credentials when assumed.

Key Concepts of Roles

  • Trust Relationship: Defines who is allowed to assume (use) the role — e.g., EC2 service, another AWS account, a Lambda function
  • Permissions Policy: Defines what the role can do once assumed — same JSON policy format as user policies
  • Temporary Credentials: When a role is assumed, AWS STS (Security Token Service) generates short-lived credentials (Access Key ID, Secret Access Key, Session Token) — they expire automatically
  • Role Assumption: The act of "taking on" a role to gain its permissions temporarily

Common Role Types

Role TypeWho Assumes ItUse Case
EC2 Instance RoleEC2 instancesAllow an EC2 app to read from S3 without embedding access keys

Cross-Account RoleUsers in another AWS accountAllow Account B users to access resources in Account A
Service-Linked RoleAWS managed servicesCreated and managed by AWS for specific service integrations
Federated RoleExternal identity providersAllow corporate directory (Active Directory) users to access AWS

Why Roles Are Preferred Over Embedding Credentials in AWS Services

  • No static credentials: Access keys embedded in code/config can be leaked in version control or logs
  • Auto-rotation: Temporary credentials expire automatically — no manual rotation needed
  • Least privilege: Roles grant only the permissions needed for the task
  • Auditability: CloudTrail logs which role performed which action
  • No sharing: Each service instance gets its own temporary credentials

1.8 IAM Policies — Structure & Types

Definition
An IAM Policy is a JSON document that defines permissions. It specifies what actions are allowed or denied on which AWS resources, optionally under certain conditions.

Policy JSON Structure

{
  "Version": "2012-10-17",          // Policy language version (always use this)
  "Statement": [              // Array of permission rules
    {
      "Sid": "AllowS3ReadAccess",  // Optional: Statement ID (label)
      "Effect": "Allow",          // Allow OR Deny
      "Action": [              // What action(s) are permitted
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [            // Which AWS resource(s)
        "arn:aws:s3:::my-bucket",
        "arn:aws:s3:::my-bucket/*"
      ],
      "Condition": {           // Optional: extra conditions
        "StringEquals": {
          "aws:RequestedRegion": "us-east-1"
        }
      }
    }
  ]
}

Explaining Every Field

FieldRequiredValuesMeaning
VersionYes"2012-10-17"Policy language version — always use 2012-10-17
StatementYesArray of rulesOne or more permission rules in the policy
SidNoAny stringStatement identifier — a label for the rule
EffectYesAllow / DenyWhether to permit or block the action. Deny overrides Allow.
ActionYesservice:operationThe AWS API action(s) — e.g., s3:GetObject, ec2:StartInstances
ResourceYesARN or *The specific AWS resource(s) the action applies to. * = all
ConditionNoKey-value pairsExtra constraints — time, IP, MFA, region, tags
⚠️ Explicit Deny Always WinsIf multiple policies apply and one says Deny, the action is ALWAYS denied — regardless of any Allow statement elsewhere.

Default Deny

  • In AWS IAM, everything is denied by default
  • You must explicitly Allow an action for it to be permitted
  • The permission evaluation order: Explicit Deny → Explicit Allow → Default Deny

1.9 Least Privilege Principle

Definition
The Principle of Least Privilege states that every identity (user, role, service) should be granted only the minimum permissions necessary to perform its intended function — and nothing more.

Why It Matters

  • Limits blast radius: If credentials are compromised, the attacker can only do what that identity was allowed to do
  • Reduces insider threats: Employees can only access what they need for their job
  • Compliance: Many security standards (PCI-DSS, HIPAA, SOC2) mandate least privilege
  • Better audit trail: Narrow permissions make suspicious activity more visible

Example

Scenario: A Lambda function processes images and stores them in S3
  • Bad practice: Grant Lambda the AdministratorAccess managed policy — it can now delete EC2 instances, modify IAM, etc.
  • Good practice: Grant Lambda only s3:PutObject on only the specific bucket it writes to

1.10 Multi-Factor Authentication (MFA)

Definition
MFA adds an extra layer of security by requiring a user to provide two or more verification factors to authenticate — something they know (password) and something they have (authentication device/code).

MFA Authentication Factors

Factor TypeWhat It IsExample
Something you knowKnowledge factorPassword, PIN
Something you havePossession factorAuthenticator app, hardware token, OTP SMS
Something you areBiometric factorFingerprint, face recognition

Why MFA Improves Security

  • Password alone is vulnerable to phishing, brute force, data breaches
  • Even if a password is stolen, the attacker still cannot log in without the second factor
  • AWS strongly recommends MFA on root user and all privileged IAM users

Important Relationships Summary

  • User ↔ Group: A user can be in multiple groups; groups cannot be nested
  • Group → Policy: Policy attached to group grants permissions to all members
  • Role ↔ Policy: Roles have permission policies (what they can do) + trust policies (who can assume them)
  • Policy → Resource: Policy's Resource field specifies the ARN of the target AWS resource
  • User ↔ Role: Users can assume roles to temporarily gain different permissions

AWS Certificate Manager (ACM)

Provision, manage, and deploy SSL/TLS certificates — automatically and at no cost

2.1 Definition & Purpose

Definition
AWS Certificate Manager (ACM) is a managed AWS service that handles the complexity of provisioning, managing, deploying, and renewing SSL/TLS certificates for use with AWS services like Elastic Load Balancing, CloudFront, and API Gateway.

Purpose

  • Eliminate manual certificate management — no more buying, installing, or renewing certs manually
  • Enable HTTPS (encrypted) communication between clients and AWS-hosted applications
  • Provide public certificates (for internet-facing sites) at no cost
  • Provide private certificates (for internal infrastructure) via ACM Private CA
  • Auto-renewal prevents certificate expiry outages

2.2 Digital Certificates, SSL, TLS & HTTPS

📜 Digital Certificate
An electronic credential that proves the identity of a server/entity and contains its public key. Issued by a trusted Certificate Authority (CA).
🔒 SSL (Secure Sockets Layer)
Older cryptographic protocol (now deprecated). Established the concept of encrypting web traffic between client and server.
🔐 TLS (Transport Layer Security)
The modern, more secure successor to SSL. The actual protocol used today for encrypting internet communication.
🌐 HTTPS
HTTP + TLS. The web protocol that uses TLS to encrypt HTTP traffic. URLs start with https:// and use port 443.

Architecture Explanation

  • TLS Termination at LB/CloudFront: The ACM certificate is installed at the load balancer or CloudFront — not on the application itself
  • Encrypted externally: All traffic between users and the load balancer is encrypted
  • Internal traffic: Traffic between load balancer and app servers may be HTTP (within AWS's private network) or HTTPS (for end-to-end encryption)
  • ACM manages the certificate: The private key of the certificate never leaves AWS — it's stored and managed by ACM

2.5 Real-World Example: HTTPS for a Web Application

ScenarioYou are launching an e-commerce website at shop.mystore.com. Customers must have a secure, encrypted connection to trust the site and submit payment info.

Why ACM Is Useful Here

  • Without a certificate, the browser shows "Not Secure" — customers won't trust the site
  • Without HTTPS, payment data travels in plaintext — major security risk
  • Buying and managing certificates from a commercial CA is costly and requires annual renewal
  • ACM provides a free, auto-renewing certificate for shop.mystore.com

Conceptual Flow

Customer visits https://shop.mystore.com
↓
Browser connects to CloudFront/ALB endpoint
↓
TLS Handshake: Server presents ACM certificate for shop.mystore.com
↓
Browser validates certificate (trusted CA, valid, not expired, domain matches)
↓
Encrypted HTTPS session established 🔒
↓
Customer safely enters payment information

ACM Advantages

  • Free public certificates for AWS-integrated services
  • Automatic renewal — no expiry surprises
  • Integrated with ALB, CloudFront, API Gateway, AppSync — one-click deployment
  • Private key never exported from AWS — highly secure
  • Supports wildcard certificates (*.mystore.com)

ACM Limitations

  • ACM certificates cannot be downloaded / exported (private key stays in AWS)
  • Only usable with supported AWS services — cannot install on a self-managed server
  • Private certificates (ACM Private CA) have an associated cost
  • Only available for domains you can validate (DNS or email)

AWS Key Management Service (KMS)

Create, manage, and control cryptographic keys to encrypt your data across AWS

3.1 Definition & Purpose

Definition
AWS Key Management Service (KMS) is a fully managed service that enables you to create, manage, and use cryptographic keys to encrypt and decrypt data. KMS integrates deeply with other AWS services to protect data at rest.

Core Concepts

🔐 Encryption
Transforming readable data (plaintext) into an unreadable format (ciphertext) using a cryptographic algorithm and key. Only those with the correct key can decrypt it.
🗝️ Cryptographic Key
A piece of data (a string of bits) used by an algorithm to encrypt or decrypt information. The security of encryption depends on protecting the key.
🔧 Key Management
The full lifecycle management of keys: creation, storage, rotation, access control, auditing, and deletion.
📦 KMS Key (CMK)
Customer Master Key — the primary resource in KMS. A logical key that KMS manages securely. Never leaves KMS in plaintext.

3.2 Encryption at Rest vs Encryption in Transit

📌 Critical DistinctionThese are two different types of encryption for different threat scenarios. AWS uses KMS for at-rest; TLS/ACM for in-transit.
AspectEncryption at RestEncryption in Transit
WhatData stored on disk / database is encryptedData moving over network is encrypted
Threat ProtectedUnauthorized physical/storage accessNetwork eavesdropping, man-in-the-middle
When ActiveWhen data is stored and not being accessedDuring network transmission

Best Practice: Use both — encrypt data at rest AND in transit for complete protection. A strongly encrypted database accessed over plain HTTP is still vulnerable.

3.3 KMS Keys — Types & Management

Key Policies

  • Every KMS key has a key policy — a resource-based policy that controls who can use and manage the key
  • Key policies are the primary way to control access to KMS keys
  • IAM policies can supplement key policies but cannot override them
  • Key policies specify: key administrators (who manages), key users (who encrypts/decrypts)

Key Rotation

  • The practice of periodically generating new key material while keeping the same KMS key ID
  • Old key material is retained to decrypt data encrypted with it
  • New data is encrypted with the new key material
  • AWS Managed Keys rotate automatically every year
  • Customer Managed Keys: rotation must be explicitly enabled (annual automatic rotation)
  • Why rotate? Limits the amount of data encrypted with any single key version — limits exposure if a key is compromised

3.4 Symmetric Encryption

Definition
Symmetric encryption uses the same single key for both encryption and decryption. The sender and receiver must both possess the same secret key.
Symmetric Encryption Flow
Plaintext Data + 🗝️ Secret Key → Encrypt → Ciphertext
--- transmission / storage ---
Ciphertext + 🗝️ Same Secret Key → Decrypt → Plaintext Data ✓
Advantages
  • Very fast — computationally efficient
  • Suitable for encrypting large amounts of data
  • Simple implementation
  • Standard: AES-256 is extremely secure
Limitations
  • Key distribution problem — how do you securely share the secret key?
  • If the key is intercepted, all encrypted data is compromised
  • Doesn't work well across untrusted channels
AWS KMS & Symmetric Keys: By default, KMS keys are symmetric (AES-256-GCM). When you call kms:Encrypt, KMS uses the symmetric key internally — the key never leaves KMS in plaintext.

3.5 Asymmetric Encryption

Definition
Asymmetric encryption uses a mathematically linked key pair: a public key (can be shared freely) and a private key (kept secret). What one key encrypts, only the other can decrypt.
Asymmetric Encryption — Sending Encrypted Data
Sender has Plaintext
encrypts using Recipient's Public Key ↓
Ciphertext
transmitted over network ↓
Ciphertext received by Recipient
decrypts using own Private Key ↓
Plaintext Recovered ✓

Digital Signatures (Asymmetric in reverse)

  • Sender signs data using their private key
  • Anyone with the sender's public key can verify the signature
  • Proves: the sender really sent this (authenticity) and the data wasn't changed (integrity)
  • Used in TLS certificates — the CA signs the certificate with its private key; browsers verify with CA's public key
Advantages
  • Solves key distribution — public key can be shared openly
  • Enables digital signatures for non-repudiation
  • Basis for TLS/HTTPS certificate trust
  • Secure key exchange over untrusted channels
Limitations
  • Computationally expensive — much slower than symmetric
  • Not suitable for encrypting large data directly
  • Key management complexity (public/private key pairs)

3.6 Envelope Encryption ⭐ Important Concept

⭐ Core KMS ConceptEnvelope encryption is how AWS services encrypt large amounts of data using KMS without sending all data through the KMS API — which would be slow and expensive.
Definition
Envelope Encryption is a technique where data is encrypted with a Data Encryption Key (DEK), and that DEK is itself encrypted with a KMS Key (master key). The encrypted DEK is stored alongside the encrypted data — like sealing a letter in an envelope.

Why Envelope Encryption?

  • KMS API has a limit — you can only encrypt up to 4 KB of data directly via kms:Encrypt
  • Real data (files, database records, videos) is much larger than 4 KB
  • Sending all data to KMS API would be: very slow, expensive, and bandwidth-intensive
  • Solution: Generate a local DEK, use it to encrypt data locally, then use KMS only to protect the DEK
Envelope Encryption — Encryption Process
🗃️ Large Plaintext Data (e.g., 100 MB file)
Step 1: Ask KMS to generate a Data Key ↓
🗝️ Plaintext DEK
(Data Encryption Key)		 + 🔐 Encrypted DEK
(encrypted by KMS Key)
Step 2: Encrypt data locally with Plaintext DEK ↓
🔒 Encrypted Data (Ciphertext)

Why It's Called "Envelope": The plaintext data is encrypted (put in an envelope) with the DEK. That envelope (encrypted data) is stored with the encrypted DEK (the key is "in the envelope"). KMS only ever handles the small DEK, not the large data.

3.7 KMS Integration with AWS Services

Amazon S3 + KMS

What Gets Encrypted
  • Object data (files, images, documents) stored in S3 buckets
  • Each object can be encrypted with its own DEK
Encryption Flow
  • You upload a file → S3 requests a DEK from KMS → S3 encrypts the file locally with the DEK → stores encrypted file + encrypted DEK in S3 → plaintext DEK discarded
  • On download: S3 retrieves encrypted DEK → asks KMS to decrypt it → uses DEK to decrypt file → returns plaintext file to you
Options: SSE-S3 (S3 managed), SSE-KMS (KMS managed — more control), SSE-C (customer provided keys)

Amazon EBS + KMS

What Gets Encrypted
  • EBS volume data — the entire block storage volume is encrypted
  • Snapshots of encrypted volumes are also encrypted
Encryption Flow
  • Create encrypted EBS volume → specify KMS key → AWS generates a volume encryption key (DEK) encrypted by KMS key → all data written to disk is encrypted at the block level → EC2 reads/writes transparently (decryption happens in the hypervisor)
Key point: EC2 instance is unaware of encryption — it reads plaintext; encryption/decryption is handled transparently by the infrastructure

Amazon RDS + KMS

What Gets Encrypted
  • Database storage files (data files, logs, backups, snapshots)
  • Encryption is at the storage layer — not the application layer
Encryption Flow
  • Create RDS instance with encryption enabled → specify KMS key → RDS uses envelope encryption → all storage I/O is encrypted → automated backups and snapshots are also encrypted
Important: Encryption must be enabled at RDS instance creation — cannot encrypt an existing unencrypted instance directly (must snapshot → copy with encryption → restore)

KMS Advantages

  • Centralized key management — one service for all your encryption keys
  • Audit trail via CloudTrail — every KMS API call is logged
  • FIPS 140-2 validated hardware security modules (HSMs) — government-grade security
  • Deep integration with 100+ AWS services
  • Fine-grained access control via key policies + IAM
  • Key rotation support

KMS Limitations

  • Customer managed keys cost $1/month per key + API call charges
  • KMS API rate limits — high-throughput applications may hit throttling
  • Keys are regional — a key in us-east-1 cannot decrypt data in eu-west-1 (use multi-region keys for this)
  • KMS is not a secrets manager — use AWS Secrets Manager for database passwords and API keys

Related Services

Architecture Component Explanation

Layer 1: User Access (ACM / TLS)

  • All user traffic enters via HTTPS only — HTTP redirected to HTTPS
  • ACM certificate attached to ALB or CloudFront terminates TLS
  • TLS ensures encryption in transit — eavesdroppers cannot read traffic
  • Certificate validates server identity — users can trust they're on the real site

Layer 2: Access Control (IAM)

  • EC2 instances and Lambda functions have IAM Roles attached — no hardcoded credentials
  • IAM Roles grant only the permissions needed for each component (least privilege)
  • EC2 for the web tier: can read from S3 and query RDS — but cannot delete KMS keys
  • Lambda for processing: can write to DynamoDB — but cannot access EC2
  • IAM policies evaluated for every AWS API call made by any component
  • Administrators access AWS using IAM Users + MFA — not root

Layer 3: Data Encryption (KMS)

  • S3 buckets use SSE-KMS — each uploaded object encrypted with a DEK wrapped by KMS key
  • EBS volumes — OS and application data encrypted at block level using KMS
  • RDS databases — all database files, logs, and backups encrypted with KMS
  • Secrets Manager — stores DB passwords encrypted with KMS, rotated automatically
  • All encryption uses envelope encryption — KMS never directly handles large data
  • CloudTrail logs every KMS decrypt/encrypt call — full audit trail

Concept Map Explained

  • IAM is the foundation — it controls who can access what. Everything in AWS is accessed via IAM-authenticated and authorized calls. Authentication proves identity; authorization (via policies) determines permissions. Users are for humans, Groups simplify management, Roles enable services to act securely without static credentials, and Policies define the rules.
  • ACM solves the encryption in transit problem — ensuring data traveling between users and AWS services is encrypted and the server's identity is verified. It does this by managing the full lifecycle of TLS certificates, integrating with AWS load balancers and CDN, and automatically renewing them.
  • KMS solves the encryption at rest problem — ensuring stored data is unreadable without the correct key. It manages cryptographic keys securely (keys never leave KMS in plaintext), integrates with storage services (S3, EBS, RDS), and uses envelope encryption to handle large data efficiently without performance penalties.
  • Together: IAM controls access, ACM secures the network channel, and KMS protects the stored data — a complete three-layer security model for AWS applications.
📌 The Three Questions of AWS Security
  • Who are you? → IAM Authentication (username, password, MFA, access keys)
  • What can you do? → IAM Authorization (policies, roles, permissions)
  • Is the connection and data safe? → ACM (in-transit) + KMS (at-rest)
