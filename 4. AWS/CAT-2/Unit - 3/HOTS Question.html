Networking Security
Route 53 — Essentials
What it isAWS's managed DNS + Domain Registration + Traffic Routing service. Port 53 = DNS port → name "Route 53".
Public Hosted ZoneAnswers DNS queries from anywhere on internet. For public-facing apps.
Private Hosted ZoneAnswers DNS queries only within associated VPC(s). Internal microservices. Requires DNS resolution/hostnames enabled on VPC.
Health ChecksRoute 53 sends automated requests to endpoints. Unhealthy → traffic diverted. Feeds into Failover, Weighted, Multivalue policies.

HOTS trap: Geolocation ≠ Latency. Geolocation uses user's country. Latency uses measured network speed. A user in India might get better latency from Singapore region than Mumbai.
API Gateway — Essentials
What it isFully managed "front door" for APIs. Creates, secures, monitors APIs at scale. Sits after Route 53, before backend (Lambda/EC2).
Core purposeCentralizes auth, throttling, caching, monitoring — so backends don't have to handle them individually.
VPC LinkConnects API Gateway to private resources inside a VPC (internal ALB/EC2) without exposing backend publicly.
ThrottlingLimits requests/sec to protect backend. Configurable per stage/method via Usage Plans + API Keys.
CachingCaches responses for a configurable TTL → reduces backend calls & latency for repeated requests.
StageNamed deployment snapshot: dev/test/prod. Same API can have multiple stages simultaneously.

VPC — Core Concept
DefinitionLogically isolated virtual network in AWS. Full control over IP addressing, subnetting, routing, security.
Scope1 Region. Spans multiple AZs. Isolated by default.
CIDR blockTop-level IP range (e.g. 10.0.0.0/16). All subnets carved from this. Cannot overlap.
Default VPCAuto-created by AWS per region. Public subnets, IGW pre-configured. Not for production.
Elastic IPStatic persistent public IPv4. Won't change on instance stop/start. Required by NAT GW.
Internet GatewayAttached to VPC (not subnet). Enables bidirectional internet. One per VPC.
VPC Components Map
VPC (10.0.0.0/16) │ ├── Internet Gateway (attached to VPC) │ ├── PUBLIC SUBNET (10.0.1.0/24) — AZ-a │ Route Table: 0.0.0.0/0 → IGW │ Resources: LB, Bastion, NAT GW │ ├── PRIVATE SUBNET (10.0.2.0/24) — AZ-a │ Route Table: 0.0.0.0/0 → NAT GW │ Resources: App Servers, DBs │ └── Security Groups → on each resource
3-Tier: Internet → IGW → LB (public) → App servers (private) → DB (most private). Each tier's SG only allows traffic from the tier above it.
Subnets — Public vs Private
Key Rule: "Public" vs "Private" is determined ENTIRELY by the subnet's Route Table — NOT by the name, NOT by whether resources have public IPs.

Route Tables
PurposeRules (routes) that determine WHERE traffic from a subnet goes. The single factor making a subnet public or private.
Local routeAuto, non-removable. Allows all intra-VPC traffic (10.0.0.0/16 → local).
0.0.0.0/0 → IGWMakes subnet public. Bidirectional internet access.
0.0.0.0/0 → NAT GWMakes subnet private. Outbound only — no unsolicited inbound from internet.
Most specific winsRoute table picks the most specific (longest prefix) matching destination. 0.0.0.0/0 is the catch-all (last resort).

Security Groups
What it isVirtual stateful firewall at the instance/ENI level. Last layer of defense.
StatefulIf inbound is allowed → return traffic auto-allowed OUT. No need for matching outbound rule (and vice versa).
Default behaviorAll inbound DENIED by default. All outbound ALLOWED by default. You add Allow rules only.
Rule typesAllow ONLY. No explicit Deny rules. Source/destination can be IP/CIDR OR another Security Group.
Multiple SGsInstance can have multiple SGs. Rules from all are combined (union). Any Allow in any SG = traffic allowed.
AspectSecurity GroupNetwork ACL (NACL)
LevelInstance/ENI levelSubnet level
StateStateful (return auto-allowed)Stateless (must write return rules)
Rule typesAllow onlyAllow AND Deny
EvaluationAll rules evaluated (union)Numbered order, first match wins
ScopeOnly associated resourcesAll resources in subnet
Common rule: DB SG allows port 3306 only from App tier's Security Group (not IP). This scales automatically when app server IPs change.
NAT Gateway
PurposeLets private subnet resources initiate outbound internet without being reachable from internet (one-way NAT).
Where it livesDeployed in a PUBLIC subnet. Needs an Elastic IP. Uses the public subnet's IGW route to reach internet.
How private subnet uses itPrivate route table: 0.0.0.0/0 → NAT GW. NAT GW translates private IP to its Elastic IP for outbound.
Why no inbound?NAT only forwards responses to connections it initiated. No route from internet exists to private instance. Internet cannot start new connection to private IP.
Private EC2 → Private Route Table → NAT Gateway (Public Subnet, Elastic IP) → Internet Gateway → Internet Response: Internet → NAT GW translates back → Private EC2 ✓
AspectNAT GatewayInternet Gateway
DirectionOutbound-only (private → internet)Bidirectional
Used byPrivate subnetsPublic subnets
Elastic IPRequiredNot needed
CostHourly + per GB dataFree
Public reachabilityNoYes (if resource has public IP)
NAT Gateway is per-AZ. For HA, deploy one NAT GW per AZ (costs more). Single NAT GW = single point of failure for outbound.
IAM — Identity & Access Management
What it isGlobal AWS service. Manages who (identity) can access AWS and what (access) they can do. Free.
Authentication"Who are you?" → Verify identity (password, MFA, access keys). Happens first. Failure = login rejected.
Authorization"What can you do?" → IAM policies grant/deny actions. Happens after auth. Failure = 403 Access Denied.
DefaultEverything is DENIED by default. Must explicitly Allow. Explicit Deny always wins over Allow.
Permission eval orderExplicit Deny → Explicit Allow → Default Deny
IAM Components
Root UserAccount owner. Unrestricted. Never use for daily tasks. Enable MFA immediately. Only root can: close account, change email, enable MFA-delete on S3.
IAM UserPersistent identity (person/app). Has long-term credentials: password (console) or access keys (CLI/API). No permissions by default.
IAM GroupCollection of users. Policy on group applies to all members. No nested groups. No credentials. Groups ≠ login.
IAM RoleAssumable identity with temporary credentials (via STS). No long-term keys. Used by AWS services, cross-account, federated users.

Least Privilege Principle
Grant only the minimum permissions needed for the task. Nothing more.
Bad: Lambda with AdministratorAccess.
Good: Lambda with s3:PutObject on only the specific bucket it writes to.

MFA — Multi-Factor Auth
Factor 1Something you know — password/PIN
Factor 2Something you have — authenticator app (TOTP), hardware token
Factor 3Something you are — biometric
Enable MFA on root user immediately. Even if password stolen, attacker can't login without 2nd factor.
ACM — Certificate Manager
What it isManaged service to provision, manage, deploy, auto-renew SSL/TLS certificates for AWS services. Enables HTTPS.
Public certsFree. For internet-facing sites. Trusted by all browsers. DNS or Email validation required.
Private certsACM Private CA — costs money. For internal microservices. Trusted only within org.
Used withALB, CloudFront, API Gateway, AppSync. Cannot be exported — private key never leaves AWS.
Auto-renewalACM renews ~60 days before expiry automatically (DNS validation). Prevents expiry outages.
Wildcard*.example.com covers all subdomains (shop, api, www...) with one certificate.

KMS — Key Management Service
What it isFully managed service to create, manage, use cryptographic keys. Protects data at rest. Integrates with 100+ AWS services.
KMS Key (CMK)Customer Master Key. Primary resource. Never leaves KMS in plaintext. Logical key with ID/ARN.
Key policyResource-based policy on every KMS key. Primary access control. IAM can supplement but cannot override key policy.
AuditEvery KMS API call logged in CloudTrail. Who used which key, when, from where.
RegionalKeys are regional. Key in us-east-1 cannot decrypt data in eu-west-1. Use multi-region keys for cross-region.
KMS ≠ Secrets ManagerKMS manages encryption keys. Use Secrets Manager for DB passwords and API keys.

⭐ Envelope Encryption — Core KMS Concept
Why needed: KMS can only encrypt up to 4 KB directly. Real data is much larger. Sending all data to KMS = slow + expensive.
ENCRYPTION
Large Data (e.g. 100MB file) Step 1: Ask KMS → generate DEK → Plaintext DEK + Encrypted DEK Step 2: Encrypt data locally with Plaintext DEK → Encrypted Data (Ciphertext) Step 3: Discard Plaintext DEK from memory Store: [Encrypted Data] + [Encrypted DEK]
DECRYPTION
Retrieve: Encrypted Data + Encrypted DEK Step 1: Send Encrypted DEK to KMS → KMS returns Plaintext DEK (KMS checks your permissions first) Step 2: Use Plaintext DEK to decrypt data → Plaintext Data ✓ Step 3: Discard Plaintext DEK
TermRoleKey Point
KMS Key (KEK)Master key / Key Encryption KeyEncrypts the DEK. Never leaves KMS. Used minimally.
DEKData Encryption KeyGenerated per-object. Encrypts actual data. Discarded after use. Stored encrypted.
CiphertextEncrypted dataResult of DEK encrypting the data
Encrypted DEKWrapped keyDEK encrypted by KMS Key. Stored alongside ciphertext.

🔵 Route 53 — HOTS Questions
Q: A company needs to route 5% of traffic to a new backend for testing, and the rest to the old backend. Which Route 53 policy and why?
→ Weighted Routing. Set old backend weight 95, new backend weight 5. Route 53 distributes traffic in this ratio. This is canary/gradual deployment — if new backend has issues, only 5% of users affected.
Q: A user in India connects to your API. They should go to the closest region, but your Geolocation policy routes them to EU. Why could this happen?
→ Geolocation uses DNS resolver's IP (ISP), not user's actual location. If the resolver is geolocated incorrectly (e.g. Indian ISP using a US-registered resolver), Route 53 may misidentify location. Geolocation ≠ Latency routing.
Q: Why can't you use a CNAME record for example.com but you can for www.example.com?
→ CNAME at zone apex (root domain) violates DNS RFC. The zone apex requires NS and SOA records, which conflict with CNAME restrictions. Use Alias record instead — Route 53 specific, works at zone apex, free, auto-tracks AWS resource IP changes.
Q: Failover vs Multivalue routing — when to use which?
→ Failover: Primary-Secondary DR setup. Traffic goes to secondary ONLY when primary's health check fails. Multivalue: Returns multiple healthy IPs for simple client-side load balancing. Not a replacement for ALB — just DNS-level health awareness with random selection.
🟣 API Gateway + VPC — HOTS Questions
Q: Why use API Gateway instead of exposing Lambda directly via a public URL?
→ API Gateway centralizes: auth (IAM/Cognito/Lambda authorizer), throttling (rate limiting to protect Lambda from overload), caching (reduce Lambda invocations), monitoring (CloudWatch), request validation. Direct Lambda URL lacks these — you'd have to build each manually.
Q: A private EC2 can ping google.com, but the internet cannot reach it. How is this architecture set up?
→ EC2 in private subnet. Private subnet route table: 0.0.0.0/0 → NAT Gateway. NAT Gateway in public subnet (with Elastic IP) → Internet Gateway → internet. NAT translates private IP to Elastic IP for outbound. No route from internet to private EC2 exists → cannot initiate inbound connections.
Q: You named a subnet "public-subnet" but resources in it can't reach the internet. What's wrong?
→ Naming has NO effect. The subnet's Route Table must have 0.0.0.0/0 → Internet Gateway. Also check: (1) VPC has an Internet Gateway attached, (2) the resource has a public IP assigned, (3) Security Group allows outbound traffic.
Q: Security Group vs NACL — which to use for blocking a specific IP?
→ NACL. Security Groups only support Allow rules — you cannot explicitly deny a specific IP. NACLs support both Allow and Deny rules at subnet level. Add a Deny rule with lower rule number (higher priority) than any Allow rule for that IP.
🔵 IAM — HOTS Questions
Q: A developer accidentally attached AdministratorAccess to a Lambda role. Even if the Lambda has this policy, what else limits what it can do?
→ Resource-based policies on the target resource can still deny access. Also, Permissions Boundaries on the role set a maximum ceiling — even AdministratorAccess can't exceed the boundary. And SCPs (Service Control Policies) in AWS Organizations can further restrict what any entity can do.
Q: Why use IAM Roles for EC2 instead of embedding access keys in code?
→ Embedded keys: (1) can be accidentally committed to Git and exposed, (2) hard to rotate (manual process), (3) shared across instances. Roles provide: temporary credentials via STS (auto-expire), automatic rotation, no key to leak, each instance gets fresh credentials, CloudTrail logs role usage.
Q: Policy A allows s3:DeleteObject. Policy B denies s3:DeleteObject. Both attached to user Alice. Can Alice delete S3 objects?
→ No. Explicit Deny always wins. Even though Policy A explicitly allows, Policy B's explicit deny overrides it. Order: Explicit Deny → Explicit Allow → Default Deny. Any Deny anywhere = blocked.
Q: Difference between Trust Policy and Permissions Policy on a Role?
→ Trust Policy: WHO can assume (use) this role (e.g. EC2 service, another account, Lambda). Permissions Policy: WHAT the role can do once assumed (e.g. s3:GetObject on my-bucket). Both must be set for a role to work.
🟢 ACM + KMS — HOTS Questions
Q: A customer says "our database is encrypted using ACM." Is this correct?
→ No. ACM manages TLS certificates for encryption in transit (network). Database encryption (at rest) uses KMS with S3/EBS/RDS integrations. ACM cannot be used with/on RDS directly. It's a common conceptual confusion.
Q: Why does AWS use Envelope Encryption instead of encrypting everything directly with the KMS key?
→ KMS can only encrypt ≤4 KB directly. Real data (files, DB records) is much larger. Sending all data to KMS API would be slow, expensive, and bandwidth-intensive. Envelope encryption: use KMS only to protect a small DEK, then use DEK to encrypt large data locally. KMS stays fast and cheap; large data encryption is efficient.
Q: You need to encrypt S3 data AND need to audit exactly which IAM user decrypted a specific file. Which encryption option?
→ SSE-KMS with a Customer Managed Key (CMK). AWS Managed Key (SSE-KMS with aws/s3) logs to CloudTrail too, but CMK gives you full control over key policy, the ability to restrict individual users via key policy, and complete audit trail in CloudTrail. SSE-S3 uses AWS-managed key with less audit granularity.
Q: Can you use the same ACM certificate in us-east-1 for a CloudFront distribution AND an ALB in ap-south-1?
→ For CloudFront: certificate MUST be in us-east-1 (CloudFront is global but requires certs in us-east-1). For ALB in ap-south-1: certificate must be in ap-south-1. ACM certificates are regional for most services. So you'd need two certificates — one in each region.
Q: HTTP vs HTTPS: why is HTTPS considered more secure beyond just encryption?
→ HTTPS provides: (1) Encryption — data unreadable in transit, (2) Authentication — certificate proves server is who it claims (prevents impersonation), (3) Data integrity — TLS MAC ensures data wasn't tampered with in transit. HTTP provides none of these — plaintext, no identity verification, no integrity check.
Critical Confusions — Quick Reference

CNAME vs AliasCNAME: extra lookup, can't use at zone apex, charged. Alias: Route 53 internal, zone apex OK, free, auto-tracks AWS resource.
